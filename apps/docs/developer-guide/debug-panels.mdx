## Overview

The `/debug` area is the local diagnostics workspace for Radarboard. Use it when a widget, plugin, integration, cache entry, assistant action, or webhook flow behaves differently than expected in development.

Each panel is read-only unless the page clearly presents an action such as refresh, inspect, or retry.

## Navigation model

The sidebar is ordered around the most common troubleshooting flow:

1. **Overview** - confirm that extensions, services, and cached data are wired correctly.
2. **Assistant** - inspect AI conversations, traces, memory, and generated reports.
3. **Runtime** - inspect the lower-level event, span, client issue, and webhook evidence.
4. **Dev Sandboxes** - isolate extension descriptors and rendering behavior.

This keeps the first stop useful for most dashboard problems while leaving room to add future pages without creating one long undifferentiated system list.

## Naming conventions

Debug page names should describe the thing being inspected, not the implementation module:

- Use **Extension Health** instead of registry internals.
- Use **Response Cache** instead of cache.
- Use **LLM Traces** instead of traces.
- Use **Performance Spans** instead of spans.
- Use **Debug Events** instead of events.

When adding a new page, prefer names that answer “what will I inspect here?” and keep the sidebar label short enough to scan.

## Overview panels

### Extension Health

Use **Extension Health** as the first stop for modularity and registration issues. It shows registered extensions, data sources, widget resolvers, health score, issues, and usage counters.

Start here when a dashboard widget says a provider is missing, a sandbox is empty, or an extension appears installed but does not work.

### Service Health

Use **Service Health** to inspect integration availability, latency, error rates, and recent failures.

Start here when provider data is unavailable, slow, or failing after registration is confirmed.

### Response Cache

Use **Response Cache** to review cached API responses, fetch times, TTLs, and expiration state.

Start here when a dashboard value looks stale or when a successful provider response is not reflected in the UI.

## Assistant panels

### Conversations

Use **Conversations** to inspect saved assistant threads and their associated project metadata. This is useful when debugging conversation history, project routing, or stale context.

### LLM Traces

Use **LLM Traces** to inspect assistant requests, token usage, model latency, estimated cost, and trace-level metadata.

Start here when an AI response is slow, unexpectedly expensive, or missing context.

### AI Memory

Use **AI Memory** to review persistent assistant facts stored across conversations. This helps verify whether the assistant is carrying the right project context into later runs.

### Reports

Use **Reports** to find generated analysis reports and exports created from assistant workflows.

## Runtime panels

### Debug Events

Use **Debug Events** to search durable debug events emitted by chat, plugins, integrations, MCP tools, and client surfaces.

Start here when you know something happened but need a chronological event trail.

### Performance Spans

Use **Performance Spans** to inspect timed runtime spans across API routes, integrations, plugins, and background work.

Start here when a feature works but feels slow.

### Client Issues

Use **Client Issues** to inspect grouped browser runtime errors, API failures, and React client issues.

Start here when the problem appears only in the browser or after a client interaction.

### Webhook Relay

Use **Webhook Relay** to inspect inbound webhook events, payload summaries, and delivery outcomes.

Start here when testing inbound provider webhooks or local webhook forwarding.

## Recommended flows

### Extension-driven dashboard issue

1. Open **Extension Health** to confirm the extension is registered.
2. Open **Service Health** to confirm the provider data path is healthy.
3. Open **Response Cache** to confirm the dashboard is not reading stale data.
4. Open the relevant sandbox from [Debug Sandboxes](/developer-guide/debug-sandboxes) to isolate rendering or descriptor issues.
5. Use **Debug Events**, **Performance Spans**, or **Client Issues** for lower-level runtime details.

### Assistant issue

1. Open **Conversations** to identify the thread and project context.
2. Open **LLM Traces** to inspect model calls, latency, token usage, and cost.
3. Open **AI Memory** to verify persistent context.
4. Open **Reports** if the issue involves generated outputs.
5. Use **Debug Events** or **Client Issues** if the assistant UI itself failed.

### Webhook issue

1. Open **Webhook Relay** to inspect the inbound event.
2. Open **Debug Events** for related runtime messages.
3. Open **Performance Spans** if delivery is slow.
4. Open **Service Health** if the webhook updates provider-backed data.

## Adding a new panel

Add new pages by extending the central debug registry, not by hardcoding links in the shell.

Each registry entry should include:

- a short sidebar `label`
- a clear page `title`
- a one-sentence `description`
- a `docsHref`
- a group: `overview`, `assistant`, or `runtime`

If the new page does not fit one of those groups, add a new group only when there will be more than one page in that mental model. Avoid one-page groups unless the page is a major top-level workflow.
